# Market Event Radar v11.4.45 anti-regression / security / production-readiness audit

## Release intent

v11.4.45 is not a visual patch. It closes the recurring failure class where a feature was present in source code but not actually active in production, and where an old regression test could later force the project back toward an unsafe design.

The release has three independent acceptance layers:

1. deterministic application tests;
2. security / authorization regression checks;
3. production-readiness checks for the deployed live Worker.

A source-code green light alone must never be interpreted as proof that the production live endpoint is active.

## Root causes eliminated

### 1. “Live” Worker existed but production endpoint was never connected

Earlier releases contained the Worker source while `liveMarketEndpoint` remained empty. GitHub Actions snapshots were then repeatedly fetched by the browser and could look like a live refresh even when the market value itself had not changed.

v11.4.45 changes the contract:

- the browser boots in explicit `github-fallback-only` mode;
- a successful Cloudflare production deployment must pass `/health`, snapshot, K-line and allowlist probes;
- only after that success does a separate GitHub job publish the public HTTPS endpoint to the history-free `live-runtime` branch;
- the browser loads that public endpoint dynamically with `cache: no-store`;
- the Service Worker does not precache runtime configuration;
- the UI may say “Worker 即時通道／盤中每分鐘” only when the payload was actually loaded from the Worker; otherwise it says “GitHub 備援・非即時”.

### 2. Cloudflare deployment could report success while every deploy step was skipped

Deployment authorization is now fail-closed. Missing `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` or KV namespace exits non-zero before checkout/deploy. The public endpoint is not manually configured: it is derived from the pinned Wrangler deployment output, validated, live-probed, and only then published. The deployment job runs inside the `production` GitHub Environment. Configure that Environment to allow only `main` deployments and, where your GitHub plan supports it, require your own approval before production credentials are released.

The Cloudflare credential job has only `contents: read`. The later `publish-runtime` job has `contents: write` but receives no Cloudflare API token. This separation prevents one job from simultaneously holding cloud-deployment credentials and repository-write capability.

### 3. Workflow/action supply-chain permissions were too broad in practice

Every external GitHub Action reference is pinned to a full 40-character commit SHA. `actions/checkout` has `persist-credentials: false` everywhere. Data publication receives `GITHUB_TOKEN` only on the final publication step, and `publish_data_branch.sh` uses that token explicitly for the one push instead of leaving credentials in the repository Git configuration.

Python production and test dependencies are exact-version locked rather than floating version ranges. Cloudflare Wrangler is explicitly pinned to `4.123.0` in the deployment action.

The audited external Action release pins for this build are:

- `actions/checkout` v7.0.1 → `3d3c42e5aac5ba805825da76410c181273ba90b1`;
- `actions/setup-python` v7.0.0 → `5fda3b95a4ea91299a34e894583c3862153e4b97`;
- `actions/upload-artifact` v7.0.1 → `043fb46d1a93c77aae656e7c1c64a875d1fc6a0a`;
- `cloudflare/wrangler-action` v4.0.0 → `ebbaa1584979971c8614a24965b4405ff95890e0`.

Dependabot is configured for weekly `pip` and `github-actions` update PRs. Release Verification also runs on pull requests, so an automated dependency update cannot be merged as an untested silent pin change.

### 4. A regression test preserved the unsafe Cloudflare behavior

The old test explicitly expected missing Cloudflare credentials to produce a warning and *not* fail. That meant a future “cleanup” could reintroduce the skipped-deployment behavior while tests stayed green.

The regression contract is reversed in v11.4.45: missing production authorization must fail, and the security audit fails if that behavior disappears.

### 5. TWSE day-trading verifier and production updater could disagree

The release verifier previously called one hard-coded TWSE OpenAPI URL. That URL can return a valid non-empty JSON schema unrelated to the expected day-trading amounts, producing a false contract failure. The production updater used a different candidate order.

v11.4.45 adds a shared semantic selector in `update_tw_chips.py`. It accepts a TWSE candidate only when the *production parser* can actually recover the required `volume`, `buy_amount` and `sell_amount` fields. The live verifier reuses that same selector/parser, preventing verifier/updater drift.

### 6. Remote runtime JavaScript was an unnecessary supply-chain dependency

The unpkg Lightweight Charts loader was removed. The built-in SVG candlestick renderer remains the deterministic fallback and default. No third-party runtime `<script src=https://...>` is required for the homepage.

### 7. Browser attack surface and stale code cache

All top-level pages now carry a restrictive Content Security Policy and `no-referrer` policy. External dynamic links pass through an HTTPS-only URL gate that rejects embedded credentials and unsafe schemes. Remote news images are HTTPS-only and no longer rely on inline JavaScript event handlers.

Executable same-origin JS/CSS and data are network-first in the Service Worker. Runtime configuration is never precached. Static images may remain cache-first for offline resilience.

### 8. Portfolio JSON import was unbounded and trusted arbitrary records

Import is capped at 1 MiB and 500 rows. Every symbol must exist in the known asset master, quantities/costs must be finite and bounded, duplicate symbols are normalized, and imported names cannot inject arbitrary markup because display still escapes values.

## Authorization model

### GitHub

- Default workflow permission should be set to read-only in repository settings.
- Each workflow declares only the repository permission it needs.
- All external Actions are immutable SHA pins.
- Checkout credentials are never persisted.
- `GITHUB_TOKEN` is scoped to the final live-branch publication step where possible.
- `release-verification.yml` itself is read-only.

### Cloudflare

Required production values:

- Secret: `CLOUDFLARE_API_TOKEN`
- Secret: `CLOUDFLARE_ACCOUNT_ID`
- Repository/Environment variable: `CLOUDFLARE_KV_NAMESPACE_ID`

Create the Cloudflare API token with the Cloudflare “Edit Cloudflare Workers” custom template and scope it only to the single account used by this project. Never place this token in source, runtime JSON, browser JavaScript, Actions artifacts or logs.

The public Worker endpoint is not a credential, but it is still not accepted from a hand-maintained repository variable. The deployment workflow derives it directly from `cloudflare/wrangler-action`'s `deployment-url` output, validates that it is a clean HTTPS URL, runs live readiness checks, and only then publishes it to `live-runtime`.


### Repository-setting controls that cannot be embedded in the ZIP

The package enforces least privilege inside workflow YAML, but repository-admin controls live outside source code. For the strongest setup, keep default `GITHUB_TOKEN` permissions read-only, enable the full-SHA pinning policy, restrict allowed Actions to the audited providers, protect `main` against force-push/deletion, and protect the `production` Environment. These settings must be checked in GitHub after upload.

## Production Worker protections

- read-only GET/OPTIONS API;
- fixed six-index symbol allowlist, so `/kline` cannot become an arbitrary Yahoo proxy;
- KV-backed K-line caching to reduce upstream abuse and request bursts;
- `/health` contract with version/cache-binding state;
- automatic request-time self-heal if the scheduled open-market snapshot is older than 90 seconds;
- cached last verified data when an upstream request fails;
- `nosniff`, no-referrer and no-store response headers;
- unsupported symbols/intervals return HTTP 400;
- missing KV binding returns HTTP 503 instead of pretending to be healthy.

## 15 分鐘 K 線：部署後、非阻擋能力

**15 分鐘 K 線仍屬來源相依的部署後、非阻擋能力。** Yahoo/Worker 當下若沒有可信的 15 分鐘資料，前端必須顯示不可用或過期，**不得偽造** K 棒。Release Verification 不能把外部資料供應商的短暫不可達誤判成應用程式本身損壞，但 Production Readiness 必須驗證 Worker 的基本 K-line contract。

## Permanent anti-regression gates

`release-verification.yml` now requires, in order:

- version-aware stale-file cleanup check;
- one-writer-per-live-branch audit;
- Python / JavaScript / shell syntax;
- release hygiene scan;
- workflow YAML parse;
- security and authorization audit;
- static production-readiness audit;
- strict public-data validation;
- full regression suite;
- HTTP app-shell smoke;
- Chromium runtime smoke;
- reachability-aware external source contract gate using production parsers.

The separately triggered Cloudflare deployment has an additional **live** production-readiness gate. A release can therefore distinguish “application package is valid” from “production live Worker has been authorized and deployed”.
