# v11.4.37 TPEx live diagnostic

This is a **read-only diagnostic addition**. It does not change the production parser, site UI, live-channel schema, or version number.

## Why this exists

The production release gate sees TPEx day-trading `rows=5 parsed=0`, while local fixture tests pass. Before changing the parser again, the project needs reproducible evidence of the actual TPEx live response.

## What the diagnostic records

For each relevant TPEx OpenAPI endpoint it records:

- up to 3 HTTP attempts with status, elapsed time, response size and selected safe response headers;
- JSON top-level type and row count;
- the first 5 row key sets and normalized key sets;
- truncated public row values;
- all fields that look like dates and how the current date parsers interpret them;
- current `row_date` / `valid_chip_date` results;
- for TPEx day trading, whether each row is discarded **before** field matching by the current parser;
- which volume/buy/sell field aliases or semantic matches are found;
- the current production parser result;
- for ex-dividend/dividend-plan/material sources, the current parser count and a few parsed samples.

The diagnostic intentionally exits with success when TPEx returns 4xx/5xx. A 520 is diagnostic evidence and must be preserved in the artifact instead of being confused with a diagnostic-program failure.

## How it runs

Workflow: `Diagnose TPEx live schemas`

It runs automatically when these diagnostic files are first pushed to `main`, and it can also be run manually with `workflow_dispatch`.

Artifact: `tpex-live-diagnostic-<run_id>`

Files:

- `tpex-live-diagnostic.json` — structured evidence for analysis.
- `tpex-live-diagnostic.log` — human-readable summary from the Actions log.

No parser changes should be made until this artifact has been reviewed.
