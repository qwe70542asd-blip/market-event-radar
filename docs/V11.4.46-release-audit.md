# Market Event Radar v11.4.46 production-reliability / security audit

## Scope

v11.4.46 is a full-overwrite release built from v11.4.45 after the first real Cloudflare production activation. It preserves the v11.4.45 fail-closed authorization model and fixes the failures that only became visible once the Worker actually deployed.

## Production evidence that drove this release

The v11.4.45 deployment proved that all three production values were valid and that Wrangler could upload the Worker, bind the `MARKET_CACHE` KV namespace, install the one-minute cron, and return the public endpoint `market-event-radar-live.qwe70542asd.workers.dev`.

The first production-readiness probe then ran almost immediately after Wrangler reported deployment and received HTTP 404 from `/health`. Minutes later the same `/health` endpoint returned the expected v11.4.45 JSON with `status: ok` and `cache_binding: true`. The Worker was healthy; the gate had a post-deploy propagation race.

Separately, GitHub's real Chromium release gate failed because the test itself used Playwright's string form of `wait_for_function`. That form requires JavaScript evaluation that the site's intentionally strict `script-src 'self'` CSP blocks. Weakening CSP with `unsafe-eval` would have been the wrong fix.

## v11.4.46 changes

### 1. Post-deploy propagation is retry-aware

`production_readiness.py` now probes a newly deployed Worker with bounded delays of 0, 3, 5, 10, 15 and 30 seconds before declaring `/health` unavailable. Snapshot and K-line probes also receive short bounded retries for transient upstream/cache warm-up failures.

This is a fail-closed retry, not a silent pass: if the endpoint never becomes healthy, deployment still fails and `live-runtime` is not published.

### 2. Browser smoke is CSP-safe

`browser_smoke.py` no longer contains `wait_for_function(...)`. It uses Playwright Locator/Expect assertions for calendar count, market breadth, foreign direction and delayed news recovery. The production CSP remains strict; no `unsafe-eval` exception was added.

A regression test and the security audit now fail if string-eval `wait_for_function` is reintroduced.

### 3. Exact Worker identity is pinned

The only accepted live endpoint is:

`market-event-radar-live.qwe70542asd.workers.dev`

The deploy workflow validates this exact hostname before handing the endpoint to Production Readiness or publishing it to `live-runtime`. `production_readiness.py` applies the same hostname/path allowlist.

The browser does not trust `live-runtime` solely because it contains an HTTPS URL. `runtime-config.js` validates the exact hostname and calls `/health`; it accepts the endpoint only when service identity, release version, KV binding and rate-limit binding are all healthy.

### 4. Worker API abuse resistance

The Worker remains public/read-only, GET/OPTIONS only, and keeps the six-symbol allowlist. v11.4.46 adds Cloudflare Workers native Rate Limiting through the `API_RATE_LIMITER` binding in `wrangler.jsonc.example`.

The binding uses namespace `1144601` with a 600 requests/minute limit per rate-limit key at a Cloudflare location. Snapshot and K-line routes are protected. If the binding is absent, those routes fail closed with 503 and `/health` reports degraded. Exceeded requests return HTTP 429 with `Retry-After: 60`.

No extra GitHub secret, API key or KV namespace is needed for this rate-limit binding.

### 5. Cloudflare credential scanning

The repository's security audit now recognizes the 2026 scannable Cloudflare credential prefixes:

- `cfut_` — User API Token
- `cfat_` — Account API Token
- `cfk_` — Global API Key

A matching literal in committed source fails the security gate. Existing private GitHub Secrets remain outside source control.

### 6. Authorization separation remains intact

The Cloudflare deployment job retains repository `contents: read`. The separate `publish-runtime` job receives `contents: write` but no Cloudflare API token. Checkout credentials remain non-persistent. External GitHub Actions remain pinned to full 40-character SHAs and Wrangler remains pinned to 4.123.0.

Required production configuration remains exactly:

- Secret `CLOUDFLARE_API_TOKEN`
- Secret `CLOUDFLARE_ACCOUNT_ID`
- Variable `CLOUDFLARE_KV_NAMESPACE_ID`

No `LIVE_MARKET_ENDPOINT` secret/variable is allowed.

## Permanent regression gates added in v11.4.46

The automated suite now explicitly checks that:

- the post-deploy retry schedule exists;
- the exact workers.dev hostname is enforced in deploy, readiness and browser runtime;
- browser smoke has no CSP-incompatible `wait_for_function` string eval;
- the Worker has a fail-closed native Rate Limiting binding and 429 behavior;
- Cloudflare prefixed credentials are scanned;
- runtime endpoint trust requires `/health` identity verification.

These are additive to the existing one-writer-per-live-branch, strict CSP, URL gates, bounded portfolio import, immutable Action SHA, no-persisted-checkout-credentials, exact Python dependency pins, release hygiene and live-source parser gates.

## Repository-admin controls outside the ZIP

The package cannot enable GitHub repository settings. For strongest production posture, enable main-branch protection, require the v11.4.46 verification check before merge, block force-push/deletion, keep default workflow token permissions read-only, and enable Dependabot alerts/security updates in repository settings.

Cloudflare now supports durable account-owned API tokens for CI/CD. The existing scoped user token remains valid; migrating to an account-owned token is an optional future hardening step, not a requirement for v11.4.46.

## Acceptance condition

Do not call the release production-ready merely because the ZIP passes local/static tests. After pushing v11.4.46, both of these must be green:

1. `Verify v11.4.46 stable app release`
2. `Deploy v11.4.46 live market worker`

The deploy workflow must reach the separate `publish-runtime` job. Only then can the browser consume the Worker as the verified live channel.
